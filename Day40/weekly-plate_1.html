▶ How this was built

The brain: system prompt design

The assistant is scoped tightly to one job: turning a small set of structured constraints (goal, diet, allergies, servings, time, skill, free-text notes) into a 7-day dinner plan plus a categorized shopping list. The system prompt below is sent with every request, and the user's form answers are passed as the user turn in a fixed JSON-like shape so the model always knows exactly what it's optimizing for.

Key design choices:

  • Hard output contract. The model is instructed to return only a single JSON object matching an exact schema (days → meals → ingredients/steps/macros, plus a shopping list grouped by category). This lets the frontend render recipe cards deterministically instead of parsing loose prose.
  • Safety-first constraint handling. Allergies are treated as hard exclusions, not preferences — the prompt explicitly tells the model to double-check every ingredient against the allergy list before finalizing, and to never substitute an allergen "for flavor."
  • Time-budget realism. The model is told to treat the stated weeknight time budget as a ceiling on active cooking time, not total time (marinating/baking passively is fine), and to keep ingredient lists short on rushed nights.
  • Graceful edge cases. If inputs are contradictory (e.g. vegan + "must include salmon" in notes) the model is told to resolve in favor of the explicit diet/allergy fields, note the conflict briefly in coachNote, and proceed rather than failing. If notes contain something unrelated to meal planning or abusive, it's instructed to ignore that part and still produce a valid plan.
  • Tone. A short "coach note" field carries the friendly, encouraging voice (one or two sentences), keeping personality out of the structured recipe data so the UI stays clean.

Why the UI looks like this

A generic chat box would hide the thing people actually want: a scannable week. So the interface is built around a day ribbon — index-card-style tabs (a nod to recipe cards) that switch between days — with three recipe cards per day (breakfast/lunch/dinner or however the model structures it) and a single shopping list at the bottom, grouped by grocery aisle so it's usable while actually shopping. The palette (basil green, warm paper, citrus and tomato accents) and the Fraunces/Work Sans/IBM Plex Mono type system were chosen to feel like an editorial recipe box rather than a generic SaaS dashboard, since the target user just wants to glance at it and know what's for dinner.

How to extend this

  • Add tools: connect a grocery-delivery MCP server (e.g. Instacart-style) so "Build my week" can also check off items already in the pantry, or a nutrition-database tool to verify macro numbers instead of having the model estimate them.
  • Add memory: persist the last plan and liked/disliked meals (e.g. via window.storage) so future weeks avoid repeats and learn preferences over time without re-asking the whole form.
  • Multi-step flows: turn "swap a meal" into its own follow-up call that only regenerates one day, keeping the rest of the week and shopping list stable — cheaper and faster than regenerating everything.
  • Personalization: pipe in a wearable or calendar integration so nights with late meetings automatically get the fastest recipes.
